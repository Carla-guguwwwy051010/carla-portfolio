# 12 Review

## 项目复盘

VybCall Video
是我第一次比较完整地参与一个商业产品从需求梳理、方案设计，到开发、测试和正式上线的过程。

如果只看最终页面，它其实并不是一个功能特别复杂的产品。

但真正参与之后，我发现它背后同时连接了渠道、内容、用户身份、订购、计费和商业转化。

也正因为这样，这个项目让我开始从"把一个页面做出来"，逐渐转向思考：

**这个产品为什么存在，它怎么真正跑起来，以及上线之后如何判断它有没有价值。**

------------------------------------------------------------------------

## 01 我做了什么

在项目中，我主要参与了从产品方案到上线落地的完整过程，包括：

-   根据业务背景梳理核心产品需求
-   梳理用户从渠道进入到完成订购的 User Journey
-   设计核心 User Flow 和页面结构
-   完成 H5 产品原型
-   撰写 PRD
-   参与需求评审
-   与开发沟通需求及实现方案
-   根据实际开发情况持续调整产品方案
-   补充页面状态与异常场景
-   参与产品测试与问题验收
-   跟进 Bug 修正与回归验证
-   参与上线前检查并推动产品最终落地

最终，VybCall Video 正式上线并进入实际商业化业务场景。

## 02 我对产品的理解发生了什么变化

### 产品不是功能集合，而是一条完整链路

项目刚开始时，我很容易把需求理解成：

"做一个可以试听和订购视频彩铃的 H5。"

但随着项目推进，我开始发现真正需要设计的是一条完整链路：

**用户为什么进来 → 进来之后看到什么 → 为什么愿意试听 → 为什么点击
Subscribe → 怎么完成身份验证 → 怎么完成订购 → 最终是否产生收入**

如果只优化其中一个页面，而忽略前后环节，整个产品仍然可能无法产生结果。

这让我开始更习惯从端到端的用户路径去理解产品。

------------------------------------------------------------------------

### Happy Path 只是产品的一部分

一开始画流程时，很容易关注最理想的情况：

**进入页面 → 点击订购 → 成功**

但真实产品里存在不同网络环境、身份验证、请求状态以及各种异常情况。

很多产品复杂度并不是来自功能数量，而来自：

**同一个行为，在不同状态下应该发生什么。**

因此后来在设计需求时，我会更习惯继续追问：

**如果这一步失败了呢？**

这个问题会进一步影响原型、PRD、开发和测试。

------------------------------------------------------------------------

### 原型不是最终答案

在个人项目里，我以前比较容易把原型当成最终方案。

但真实开发过程中，原型会不断受到业务规则、技术实现和实际体验的校正。

有些方案在 Figma
或流程图里看起来没有问题，真正开发出来之后才会发现需要调整。

所以我逐渐意识到：

**产品经理不是负责守住最初的原型，而是负责守住真正要解决的问题。**

方案可以变化，但需要知道为什么变化，以及调整之后是否仍然符合用户和业务目标。

------------------------------------------------------------------------

### 产品最终需要回到业务结果

这个项目给我最直接的一点认识，是产品不能只停留在"功能上线"。

VybCall Video 最开始要解决的问题就是：

**已经有视频彩铃内容，怎么让更多用户完成订购并产生商业价值？**

因此无论是广告渠道、内容推荐、页面体验还是订购流程，最终都需要回到同一条链路：

**Acquisition → Experience → Subscription → Revenue**

页面更好看、流程更完整都只是手段。

真正需要持续验证的是：

**投入的资源有没有带来有效的用户行为和业务结果。**

------------------------------------------------------------------------

## 03 如果重新做一次

如果让我重新做一次这个项目，我会更早把"数据验证"放进产品设计阶段。

在最开始设计 User Flow 的同时，就同步定义核心漏斗：

**Visit → Listen → Subscribe → Authentication → Subscription Request →
Success**

并提前确认每一个关键节点需要记录什么。

这样产品上线之后，可以更快回答：

-   用户主要在哪一步流失？
-   手机网络和 Wi-Fi 用户的转化是否存在差异？
-   哪类内容更容易产生 Subscribe 行为？
-   哪些渠道带来的用户最终更容易完成订购？
-   优化某个页面之后，核心指标是否真的发生变化？

相比上线后再考虑"应该看什么数据"，我会希望数据方案和产品方案从一开始就一起设计。

------------------------------------------------------------------------

## 04 我还会做得更好的地方

除了更早建立数据闭环，如果重新推进，我还会重点改进几个方面。

### 更早整理状态和边界场景

在主流程确定之后，就同步建立 State / Error
Checklist，而不是等开发或测试阶段再逐步补充。

### 让 PRD 更关注规则，而不是篇幅

减少重复描述页面，把更多精力放在：

-   页面进入条件
-   状态变化
-   功能规则
-   异常处理
-   验收标准

### 更系统地记录产品决策

开发过程中很多方案都会发生变化。

如果能够持续记录：

**Original Design → Problem → Decision → Final Solution**

后续复盘时会更容易理解为什么做出某个选择，也能减少团队之间的信息差。

------------------------------------------------------------------------

## 05 这个项目对我的意义

VybCall Video 并不是我做过最复杂的产品，但它是一个对我很重要的项目。

因为它让我第一次比较完整地看到：

一个需求如何从业务问题出发，被拆成用户流程和产品方案，再经过
PRD、需求评审、开发、测试，最后真正进入商业场景。

我也开始意识到，我真正感兴趣的不只是"设计一个产品"。

而是：

**理解一个真实的问题，找到可以落地的解决方案，并继续通过用户行为和业务结果判断它是否有效。**

这也是我想继续往产品经理，尤其是 AI Product Manager 方向深入的原因之一。
