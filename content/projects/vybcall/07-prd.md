# 07 PRD

## 从产品方案到可执行需求

完成业务背景、用户链路和订购流程梳理之后，下一步是把产品方案转化成研发可以理解和实现的具体需求。

在 VybCall Video 项目中，我参与了 PRD
撰写、原型设计和需求评审，并在开发过程中持续跟进需求实现。

对我来说，PRD
不只是把页面功能重新描述一遍，更重要的是把前期讨论中比较模糊的想法整理成一套相对明确的规则：

-   用户在什么情况下进入这个页面
-   页面需要展示哪些信息
-   用户可以进行哪些操作
-   点击之后系统应该发生什么
-   不同网络和用户状态下流程如何变化
-   正常和异常情况下分别如何反馈

这些内容确认清楚之后，设计、开发和测试才能围绕同一套产品逻辑推进。

------------------------------------------------------------------------

## 需求范围

本次 H5 产品需求主要围绕从内容体验到视频彩铃订购的核心链路展开。

### 01 内容浏览与试听

用户进入 H5 后，可以浏览推荐的视频彩铃内容，并对感兴趣的内容进行试听。

主要需求包括：

-   推荐内容展示
-   视频播放 / 试听
-   当前内容信息展示
-   内容切换与继续浏览
-   Subscribe 入口

这一部分主要解决用户进入页面之后"看什么"和"为什么继续操作"的问题。

### 02 用户身份验证

当用户产生订购意愿后，需要根据实际网络环境完成身份确认。

主要涉及：

-   手机网络场景下的用户身份识别
-   Wi-Fi 场景下的手机号输入
-   短信验证码获取
-   验证码提交与验证
-   验证失败后的反馈与重新操作

这里需要保证不同网络场景最终都能够进入统一的后续订购流程。

### 03 视频彩铃订购

完成身份验证后，进入核心订购流程。

主要需求包括：

-   获取当前用户选择的内容
-   发起订购
-   处理订购中的页面状态
-   接收并展示最终订购结果
-   避免用户在请求过程中重复操作

这一部分直接对应产品的核心商业目标，因此也是需求评审和测试中重点关注的流程。

### 04 推荐与继续浏览

如果用户没有立即订购当前内容，仍然可以继续浏览其他推荐内容。

主要包括：

-   推荐其他视频彩铃
-   切换内容
-   继续试听
-   从新的内容重新进入订购流程

推荐模块不仅承担内容展示，也承担继续承接用户兴趣的作用。

### 05 状态与异常处理

除了正常流程之外，PRD 中还需要覆盖实际使用过程中可能出现的不同状态。

例如：

-   输入信息不符合要求
-   身份验证未完成
-   网络请求异常
-   内容加载异常
-   订购处理中
-   订购成功
-   订购失败

具体异常类型与处理方式以项目实际实现为准。

## 页面逻辑

核心页面之间的关系可以概括为：

**渠道 / 广告**

↓

**H5 内容页面**

浏览 → 试听 → 推荐内容

↓

**点击 Subscribe**

↓

**身份验证**

Mobile Network → 用户身份识别

Wi-Fi → Phone Number → OTP

↓

**Subscription Request**

↓

**Billing**

↓

**Success / Failed / Exception**

整个 PRD
的重点不是增加更多页面，而是保证这条链路在不同用户状态下能够正常成立。

## 原型与 PRD 的配合

在项目中，我会结合原型和 PRD 一起表达需求。

原型更适合说明：

-   页面结构
-   信息层级
-   用户操作路径
-   页面之间如何跳转
-   基础交互方式

PRD 则进一步补充原型无法完整表达的内容，例如：

-   页面进入条件
-   功能规则
-   不同状态下的处理逻辑
-   按钮触发后的行为
-   异常情况
-   开发与测试需要关注的边界条件

两者结合之后，需求才能从"页面长什么样"进一步变成"产品应该怎么运行"。

## 需求评审与开发沟通

PRD 和原型完成之后，我参与了项目需求评审，并与开发团队沟通具体实现。

实际进入开发后，产品方案并不会完全停留在最初版本。

开发过程中会出现新的问题，例如：

-   原有交互在实际实现中是否合理
-   某些状态是否遗漏
-   页面和接口返回状态如何对应
-   不同场景是否需要增加反馈
-   原型中的方案是否需要根据实际实现调整

遇到这些问题时，我会继续和开发沟通，并根据实际情况调整产品方案。

因此，对我来说，PRD
并不是"写完就结束"的文档，而是需求从设计走向落地过程中的共同参考。

## 我的思考

以前我会觉得 PRD 最重要的是"写得完整"。

真正参与开发之后，我慢慢发现，比文档长度更重要的是：

**有没有把关键规则说清楚。**

如果一个按钮点击之后会出现三种状态，就需要把三种状态讲清楚；如果手机网络和
Wi-Fi 用户走的是不同路径，就不能只在原型里画一条理想流程。

很多开发阶段的问题，本质上都是前面的产品规则还不够明确。

所以后来我在写需求时，会更关注：

**开发看到这里，能不能知道应该怎么做？测试看到这里，能不能知道应该怎么验证？**

这也是我在这个项目里对 PRD 最直接的一次理解变化。
