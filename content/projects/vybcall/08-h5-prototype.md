# 08 H5 Prototype

## 从流程图到真正可以使用的页面

在完成核心 User Flow 和需求梳理之后，我开始将业务流程进一步落到具体的 H5
页面中。

这一阶段我关注的并不只是"页面怎么排版"，而是如何让前面已经确定的产品逻辑真正体现在用户操作里。

对于 VybCall Video 来说，核心体验其实很短：

**看到内容 → 试听 → 产生兴趣 → 点击 Subscribe → 完成身份验证 → 订购 →
获取结果**

因此原型设计的重点不是增加复杂功能，而是让用户能够尽可能自然地走完这条路径。

------------------------------------------------------------------------

## 01 Landing & Content Experience

用户从 TikTok、运营商广告或其他合作渠道点击进入 H5
后，首先接触的是内容体验页面。

这一页需要同时承担两个任务：

**承接广告带来的兴趣，以及让用户理解下一步可以做什么。**

因此页面主要围绕视频内容展开，用户可以直接看到当前视频彩铃，并进行浏览或试听。

同时保留清晰的 Subscribe
入口，让已经产生兴趣的用户能够快速进入订购流程。

这一阶段我尽量避免在首屏加入过多说明，因为对于广告流量来说，用户通常不会花很多时间阅读产品介绍。

相比"解释产品"，更重要的是先让用户看到内容。

------------------------------------------------------------------------

## 02 Content Recommendation

并不是每个用户都会喜欢广告对应的第一条内容。

因此除了当前视频之外，页面还需要提供其他推荐内容，让用户可以继续浏览。

这部分的产品逻辑是：

**当前内容没有产生订购 → 继续推荐其他内容 → 用户发现新的兴趣 →
再次产生订购机会**

推荐模块因此不仅是内容展示区域，也是整个转化链路的一部分。

------------------------------------------------------------------------

## 03 Subscribe Entry

Subscribe 是内容体验和商业转化之间最关键的连接点。

在原型设计中，我希望用户在产生兴趣之后能够比较容易地找到订购入口，而不是需要重新寻找下一步操作。

用户点击 Subscribe 后，页面从内容浏览状态正式进入订购流程。

从这个节点开始，页面的设计目标也从：

**鼓励探索**

转变为：

**减少干扰，帮助用户完成操作。**

------------------------------------------------------------------------

## 04 Authentication

由于不同网络环境下用户身份识别方式不同，原型需要覆盖对应的操作路径。

### Mobile Network

在支持用户身份识别的手机网络环境下，尽量减少额外的登录操作，让用户更直接地进入后续订购流程。

### Wi-Fi

Wi-Fi 环境下，需要通过手机号和短信验证码完成身份验证。

对应页面需要处理：

-   手机号输入
-   获取验证码
-   验证码输入
-   验证状态反馈
-   继续订购

这里的设计重点不是做一个完整的账号系统，而是尽量减少身份验证对订购行为的打断。

------------------------------------------------------------------------

## 05 Subscription & Result

完成身份验证后，用户进入正式订购流程。

原型中需要明确不同阶段的页面状态，例如：

**Subscribe → Processing → Result**

最终根据订购结果进入对应反馈页面。

对于用户来说，最重要的是能够明确知道：

**我刚刚的操作到底有没有成功？**

因此结果状态需要比普通页面提示更加明确，避免用户因为状态不清楚而重复操作或直接离开。

------------------------------------------------------------------------

## 06 Error & Edge States

除了主流程页面，我也需要考虑用户无法正常继续时的页面表现。

例如：

-   输入信息有误
-   验证失败
-   内容加载异常
-   网络异常
-   订购失败
-   请求处理中

这些状态在视觉上可能只是一个提示、按钮状态或结果页，但背后对应的是不同的产品逻辑。

因此在原型阶段，我开始把正常页面和异常状态一起考虑，而不是只画一条从首页到
Success 的 Happy Path。

------------------------------------------------------------------------

## Prototype Structure

整个 H5 原型可以概括为：

**Traffic Entry**

↓

**Landing / Content**

-   Video Preview
-   Content Information
-   Recommendation
-   Subscribe

↓

**Authentication**

-   Mobile Network Identification
-   Wi-Fi: Phone Number + OTP

↓

**Subscription**

-   Submit
-   Processing

↓

**Result**

-   Success
-   Failed
-   Exception

------------------------------------------------------------------------

## 从原型到开发

原型完成后，我将核心页面和交互逻辑与 PRD 一起用于需求评审和开发沟通。

进入实际开发阶段后，部分页面和交互也会根据真实实现情况继续调整。

这让我意识到，原型并不是产品的最终答案。

它更像是产品、开发和测试之间讨论问题的一种方式。

当技术实现、业务规则或异常状态发生变化时，产品方案也需要同步调整。

因此这个项目中的原型并不是"画完之后交给开发"，而是伴随着需求评审、开发沟通和测试持续迭代。

## 我的工作

在 H5 Prototype 阶段，我主要参与：

-   将 User Flow 转化为具体页面结构
-   梳理页面之间的跳转关系
-   设计核心 H5 页面与交互
-   补充登录、订购和结果状态
-   根据需求评审反馈调整原型
-   与开发沟通页面及交互实现
-   根据开发和测试反馈持续优化方案

------------------------------------------------------------------------

## 我的思考

以前做个人项目时，我更容易把原型理解成"把想法画出来"。

但进入真实项目以后，我发现原型还有另外一个很重要的作用：

**让不同角色对同一个需求形成相对一致的理解。**

一个页面为什么存在、按钮点击之后发生什么、不同状态下应该显示什么，这些都需要通过原型和
PRD 一起被讲清楚。

所以相比单纯追求页面是否精致，我现在会更关注：

**这个原型能不能把产品逻辑说明白，以及开发能不能根据它继续往下实现。**
