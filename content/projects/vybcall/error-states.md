# 06 Error States

## 不只设计 Happy Path

在梳理完核心订购流程后，我继续检查了流程中的异常情况。

对于 VybCall Video 来说，用户从进入 H5 到完成订购，需要经过内容加载、身份验证、验证码、订购请求和计费等多个环节。

任何一个环节出现问题，都可能导致用户无法继续。

因此，除了正常流程之外，我也需要考虑：

**当系统没有按照预期运行时，用户看到什么，以及下一步还能做什么。**

---

## 01 验证码异常

Wi-Fi 用户需要通过手机号和短信验证码完成身份验证，因此验证码是一个比较容易产生中断的节点。

需要考虑的状态包括：

- 手机号格式不正确
- 验证码输入错误
- 验证码失效
- 验证码未收到
- 验证码发送失败
- 短时间内重复获取验证码

对于这些情况，不能只告诉用户“验证失败”。

更重要的是让用户知道：

**发生了什么，以及下一步应该怎么处理。**

例如验证码输入错误时，用户可以重新输入；

没有收到验证码时，可以在允许的时间后重新获取；

手机号格式错误时，则应该在提交前尽早提示。

---

## 02 网络异常

H5 产品依赖网络完成内容加载、身份验证和订购请求。

如果用户当前网络不稳定，可能出现：

- 页面内容加载失败
- 视频无法正常播放
- 请求长时间没有响应
- 登录过程中断
- 订购请求失败

这类问题对用户来说通常是不可理解的。

用户并不知道是前端、接口还是网络出现了问题，他只会感受到：

“这个页面不能用了。”

因此异常提示需要尽量避免暴露技术信息，而是提供明确、可执行的下一步操作，例如：

**重新加载 / Retry / Check Network**

---

## 03 订购异常

用户完成前面的操作后，最终还需要真正发起订购。

这是整条链路中最接近商业转化的节点，也是需要重点保证体验的部分。

如果订购没有正常完成，需要区分：

- 请求正在处理中
- 订购成功
- 订购失败
- 请求异常

尤其需要避免一种情况：

**系统状态不明确，但用户不知道自己到底有没有订购成功。**

如果反馈不清楚，用户可能重复点击 Subscribe，也可能直接退出页面。

因此结果页需要尽可能明确地告诉用户当前状态，并提供对应的下一步操作。

---

## 04 内容异常

除了订购本身，内容体验也可能影响后续转化。

例如：

- 视频加载失败
- 当前内容不可播放
- 内容信息加载失败
- 推荐内容加载异常

对于内容型产品来说，如果用户进入页面后第一条内容就无法正常体验，很可能还没有进入订购流程就已经流失。

因此内容异常同样需要纳入整体产品状态设计。

---

## Error State Framework

在整理异常状态时，我逐渐形成了一套比较简单的检查方式：

| Scenario | What happened? | User sees | User can do |
|---|---|---|---|
| 手机号格式错误 | 输入不符合要求 | 明确的格式提示 | 修改手机号 |
| 验证码错误 | 验证未通过 | 验证失败提示 | 重新输入 |
| 验证码未收到 | 用户无法继续验证 | 未收到验证码提示 | 重新获取 |
| 网络异常 | 请求无法正常完成 | 网络异常提示 | Retry |
| 内容加载失败 | 视频无法正常体验 | 加载失败状态 | Reload / Retry |
| 订购处理中 | 暂未获得最终结果 | Processing | 等待结果 |
| 订购失败 | 本次订购未完成 | Failed | Retry / 返回 |
| 订购成功 | 订购完成 | Success | 继续浏览 |

> 注：具体异常状态与处理方式以项目实际实现为准。

---

## 从异常设计到测试

异常状态梳理完成之后，它也会反过来影响测试。

测试时不能只验证：

**“我能不能从首页正常走到订购成功？”**

还需要主动去检查：

- 输入错误手机号会发生什么？
- 验证码错误后能不能继续操作？
- 重复点击按钮会发生什么？
- 网络请求失败时页面是否有反馈？
- 视频加载失败时页面是否还能继续使用？
- 订购失败之后用户有没有下一步？

这样一来，Error States 不再只是几个错误弹窗，而是逐渐变成测试 Case 的一部分。

---

## 我的思考

这个项目让我比较明显地意识到：

**产品流程不是一条线，而是一组状态。**

画 User Flow 时，我们很容易关注用户“应该怎么走”。

但真实用户和真实系统并不会永远按照 Happy Path 运行。

所以后来我在检查需求时，会开始习惯多问一句：

**“如果这一步没有成功，会发生什么？”**

这个问题看起来很简单，但它会继续影响页面状态、交互反馈、PRD、开发实现以及最后的产品测试。

对我来说，这也是从“把页面画出来”到“考虑产品怎么真正跑起来”的一个变化。
