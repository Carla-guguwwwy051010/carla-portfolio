## 1. 文档目的

本 PRD 用于统一 Personal-OS 的产品定位、目标用户、信息架构、功能范围、数据规则、交互原则、验收标准和后续迭代方向。

Personal-OS 当前已具备可运行的单文件原型，覆盖 Dashboard、PM Workspace、自主学习、创造中心、日记复盘、家教兼职、体验放松和身体健康等模块。本 PRD 不要求重构当前技术架构，而是在现有能力基础上明确 V1.0 的产品闭环与验证标准。

---

## 2. 产品概述

### 2.1 产品名称

Personal-OS（个人操作系统）

### 2.2 一句话定义

一个帮助多线程成长者统一承接工作、学习、兼职、备考与生活状态的个人系统，让每一种身份都被看见、被记录，并在身心可持续的前提下持续前进。

### 2.3 核心命题

Personal-OS 不是以“效率最大化”为目标的任务工具，而是一个“身份完整性的容器”。

它需要解决的并非单纯的任务管理问题，而是：

- 多重身份的信息分散在不同工具中，无法形成完整的自我叙事；
- 不同角色争夺时间和注意力，容易产生持续的内疚与失控感；
- 用户能看到结果，却看不到长期积累和过程性成长；
- 身心状态常被当作完成任务后的附属项，而不是承载行动的地基。

### 2.4 产品价值主张

1. **统一承接**：让实习、家教、备考、学习和生活状态进入同一套系统。
2. **身份平权**：不默认工作比学习重要，也不默认产出比休息重要。
3. **过程可见**：记录行动、状态、复盘与成长，而不只记录待办结果。
4. **开箱即用**：通过预设结构降低搭建成本，不要求用户先设计一套系统。
5. **温柔可持续**：将身心健康视为其他行动的基础条件，而非普通效率指标。

## 3. 背景与机会

### 3.1 用户问题背景

目标用户同时承担多种长期身份，例如实习生、产品经理、家教老师、备考者、自主学习者和普通生活者。现有工具通常按任务、笔记、日历或健康数据单点切割，用户被迫在多个系统之间切换。

这种分散带来的核心问题包括：

- 信息散落：项目、课程、备考记录、心情和健康无法互相解释；
- 身份割裂：每个工具只看见用户的一部分；
- 维护成本高：搭建和维护系统本身成为额外负担；
- 反馈不足：缺少跨模块的日/周回顾，难以感受到持续进展；
- 休息污名化：放松和健康常被视为“没做正事”。

### 3.2 竞品机会

根据 Notion 竞品分析：

- Notion 的核心是“自由画布”，Personal-OS 的核心应是“预设结构 + 身份关怀”；
- Notion 的自由度带来持续被用户验证的上手门槛，用户需要自行试错搭建；
- 模板生态在一定程度上替代官方产品解决结构搭建问题；
- Personal-OS 可以将多身份管理所需的常用结构原生内置，缩短“从需求到可用系统”的路径。

同时必须控制反向风险：预设结构过强可能让用户产生“不属于我”的疏离感。因此，Personal-OS 应坚持“骨架固定、内容可调”的原则。

## 4. 用户研究：JTBD 深挖

### 4.1 核心用户画像

**姓名**：阿川  
**身份**：实习生、家教、备考者、学习者，也是需要被完整看见的普通人。  
**代表性表达**：

> 我不想活成好几个互不相干的角色。

### 4.2 功能性任务（Functional Jobs）

- 当我同时推进多个身份下的事项时，我想在一个地方查看和记录进展，以便减少切换与遗漏；
- 当我完成一次课程、学习、项目推进或休息活动时，我想快速记录结果，以便形成长期积累；
- 当我开始一天或结束一周时，我想看到各身份的状态，以便决定下一步关注什么；
- 当计划改变时，我想方便地调整记录，而不是重建整套系统。

### 4.3 情绪性任务（Emotional Jobs）

- 我希望系统让我感到“我已经做了很多”，而不是不断提醒我还没完成什么；
- 我希望休息、疲惫和情绪波动被合理看见，而不是被当作效率失败；
- 我希望不同身份能够共存，不需要通过牺牲其中一个证明另一个更重要；
- 我希望回顾时能看到成长轨迹，而不是只剩零散结果。

### 4.4 社会性任务（Social Jobs）

- 我希望能够清晰说明自己在不同角色中的投入与成果；
- 我希望积累可用于汇报、复盘、作品集或面试的过程材料；
- 我希望对学生、项目合作方或未来的自己保持可靠和有交代。

### 4.5 触发场景

| 场景 | 用户当前行为 | 核心痛点 | Personal-OS 机会 |
|---|---|---|---|
| 早晨规划 | 打开多个 App 检查日程和任务 | 不知道今天最该关注哪个身份 | Dashboard 给出跨身份概览 |
| 实习推进 | 在文档、聊天和待办间切换 | 产出与思考无法沉淀 | PM Workspace 统一项目与资产 |
| 家教结束 | 临时在聊天框或备忘录记录 | 历史课程与未来安排混在一起 | 学生—课程—安排三层结构 |
| 备考学习 | 分散记录学习时间和错题 | 难以看到阶段进度 | Learning 聚合计划、记录与进度 |
| 情绪波动 | 不记录或只写零散日记 | 状态无法与行动关联 | Journal 记录心情、能量与总结 |
| 主动休息 | 休息后产生“浪费时间”感 | 缺少正向确认和复盘 | Experience 完成计划并生成体验记录 |
| 周末复盘 | 手工拼接多个来源 | 成本高，容易放弃 | 跨模块周总结与成长反馈 |

## 5. 产品目标与非目标

### 5.1 V1.0 产品目标

1. 用户能在 3 分钟内理解产品结构并完成第一条记录；
2. 用户能在一个系统中维护至少四种长期身份的关键数据；
3. 每个核心对象具备真实的新增、查看、编辑、删除和本地持久化能力；
4. Dashboard 能聚合当天最重要的状态与行动信息；
5. 用户能完成“记录 → 行动 → 完成 → 复盘”的基本闭环；
6. 系统通过温和反馈增强持续使用意愿，而不是制造任务压力。

### 5.2 V1.0 非目标

- 不做多人协作、权限和组织空间；
- 不做复杂块编辑器或 Notion 式无限页面树；
- 不做完整云端同步和账号体系；
- 不做专业医疗、心理诊断或健康建议；
- 不以 AI 自动决策替代用户判断；
- 不追求覆盖所有个人管理场景；
- 不在 V1.0 重构单文件架构或拆分前后端。

## 6. 产品原则

### 6.1 身份平权

工作、学习、家教、日记和休息在产品表达上不设置隐性价值排序。完成一次休息计划，也应获得与完成一次任务相同的正向确认。

### 6.2 健康是地基，不是 KPI

Experience / 身心健康应作为贯穿性状态层影响 Dashboard 和行动建议，不应只作为与其他模块平级的孤立入口。

### 6.3 预设骨架，局部可调

- 固定核心信息结构，降低搭建门槛；
- 允许用户调整模块显隐、卡片顺序、字段内容和个人目标；
- 不要求用户理解数据库、关系或模板概念。

### 6.4 记录成本低于收益

常用记录应在 30 秒内完成；字段分为必填与可选，避免一次录入过重。

### 6.5 完成优于完美

允许不完整记录、后续补充和草稿状态。产品反馈重点是“已被记录”，而非要求用户填写所有字段。

### 6.6 本地优先与数据自主

V1.0 数据默认只保存在用户浏览器；提供导入、导出与清空能力，并明确告知清理浏览器数据的风险。

## 7. 信息架构

### 7.1 目标三层结构

**第一层：Dashboard（枢纽）**  
聚合今日状态、当前行动、即将发生的事项和近期成长反馈。

**第二层：四个行动板块**

- Learning：备考、阅读、AI 技术学习、兴趣探索；
- PM Workspace：实习/产品项目、任务、资产与职业成长；
- Journal：每日状态、心情、能量和复盘；
- Tutoring：学生信息、历史课程与未来课程安排。

**第三层：Experience / 身心健康地基**  
以贯穿性状态条、Dashboard 卡片和独立详情入口共同呈现，负责休息计划、体验记录、身体状态和周期复盘。

### 7.2 当前实现与目标结构差异

当前 V1.0 导航还包含 Creation 与 Health 独立入口。短期保留，避免破坏已有功能；后续通过用户验证决定：

- Creation 是否并入 PM Workspace 的个人项目域，或继续作为独立创造身份；
- Health 是否与 Experience 合并为统一身心健康地基层；
- 桌面侧栏和移动底栏是否减少一级入口数量。

在验证结论产生前，不删除任何现有模块。

### 7.3 核心对象关系

| 主对象 | 子对象 | 关系 |
|---|---|---|
| 日期 DailyRecord | 关键词、心情、能量、笔记、总结 | 每日一条 |
| PM Project | PM Task | 一对多 |
| Student | Lesson / LessonPlan | 一对多，历史与未来隔离 |
| Reading / Exam / Topic | Learning Record | 一对多 |
| Creation Project | Push Log | 一对多 |
| Relax Plan | Experience Record | 完成计划时一对一自动生成，可独立补充 |

## 8. 核心用户流程

### 8.1 每日启动流程

1. 用户打开 Dashboard；
2. 查看今日心情、能量、关键词和跨模块待办；
3. 进入对应身份模块处理事项；
4. 返回 Dashboard 查看状态变化；
5. 当天结束时补充总结或心情笔记。

### 8.2 PM 项目闭环

创建项目 → 新增任务 → 调整优先级/状态 → 沉淀 PRD/周报/竞品/机制 → 周复盘。

### 8.3 学习闭环

创建学习目标/考试 → 添加学习记录 → 更新进度 → 识别薄弱点 → 调整下一步计划。

### 8.4 家教闭环

创建学生 → 查看长期概览 → 新增历史课程记录 → 创建下一次课程安排 → 上课后转为历史记录。

### 8.5 体验闭环

创建放松计划 → 标记完成 → 自动生成体验记录 → 补充地点/评分/感受 → 周总结。

### 8.6 日记闭环

选择日期 → 记录关键词/心情/能量/笔记/总结 → 自动保存 → Dashboard 同步 → 按日期回看。

## 9. 功能需求

### 9.1 Dashboard

#### 9.1.1 目标

作为全系统枢纽，在一次浏览中回答：我今天状态如何、有哪些身份正在发生事情、下一步最值得做什么。

#### 9.1.2 功能范围

| 功能 | 需求描述 | 优先级 |
|---|---|---|
| 今日状态 | 展示当天心情、能量、关键词、总结/心情笔记 | P0 |
| 空状态 | 当天无记录时提示“记录今天的状态吧”并跳转 Journal | P0 |
| 今日行动 | 聚合 PM 重点任务、课程安排、学习目标、放松计划 | P0 |
| 临近提醒 | 展示最近考试、课程和项目截止时间 | P1 |
| 身心状态条 | 在 Dashboard 视觉上突出健康承载作用 | P1 |
| 最近成长 | 展示近期完成、学习时长、体验和反思 | P1 |
| 卡片个性化 | 支持显隐或排序，不改变底层结构 | P2 |

#### 9.1.3 验收标准

- 当天 Journal 保存后，Dashboard 无需重新录入即可显示相同数据；
- 无记录时不展示示例数据伪装为用户数据；
- 所有详情入口可正确跳转；
- 移动端首屏展示不出现横向布局溢出。

### 9.2 PM Workspace

#### 9.2.1 目标

承接产品实习和项目管理身份，统一任务推进、项目状态与工作资产沉淀。

#### 9.2.2 功能范围

1. **今日驾驶舱**
   - 今日聚焦任务新增、编辑、删除；
   - 状态：待办、进行中、阻塞、完成；
   - 优先级：P0-P3；
   - 展示阻塞任务和活跃项目。
2. **项目管理**
   - 项目创建、编辑、删除；
   - 阶段：探索、定义、设计、交付、上线；
   - 项目与任务一对多；
   - 删除项目时处理关联任务。
3. **产品资产库**
   - PRD、周报、竞品分析、产品机制收藏 CRUD；
   - 支持外部链接和版本信息。
4. **用户洞察与数据分析**
   - 用户反馈、场景、分析、决策、方案；
   - 分析主题、指标、过程、结论和建议。
5. **AI 生产力中心**
   - Prompt 与工作流 CRUD；
   - 运行结果进入 AI 产出库；
   - V1.0 明确标记为模拟生成，避免误导为真实 AI。
6. **职业成长**
   - 能力成长、项目经验、面试素材、学习目标记录。

#### 9.2.3 验收标准

- 项目、任务和资产 CRUD 完整并持久化；
- 状态及优先级修改后立即更新；
- 删除项目不会留下不可访问的关联任务；
- 六个子页面均可独立打开，Console 无异常。

### 9.3 Learning

#### 9.3.1 目标

承接备考者、学习者和探索者身份，将目标、过程、进度、薄弱点和成果连接起来。

#### 9.3.2 功能范围

1. **学习 Dashboard**：今日目标、本周学习时间、当前项目、IELTS 进度、考试倒计时、AI 学习进展、最近记录。
2. **阅读管理**：想读/在读/已完成，进度、评分、笔记和洞察 CRUD。
3. **IELTS**：学习计划、听说读写词汇记录、进度追踪、薄弱点分析。
4. **备考中心**：支持多个考试；考试下包含计划、记录、进度和倒计时。
5. **AI 技术学习**：主题、学习记录、实践成果。
6. **兴趣探索**：兴趣主题、学习记录、下一步行动。

#### 9.3.3 验收标准

- 每个学习对象至少支持新增、编辑、删除；
- 关联记录按所属考试/主题隔离；
- 刷新后数据保留；
- Dashboard 统计来源于真实记录，不使用硬编码进度作为正式数据。

### 9.4 Journal

#### 9.4.1 目标

承接用户的情绪、能量和过程性成长，使状态成为行动判断的一部分。

#### 9.4.2 数据模型

每日一条 `dailyRecord`：日期、心情、能量、关键词、心情笔记、总结、创建/更新时间。

#### 9.4.3 功能范围

- 关键词新增、编辑、删除；
- 五级心情选择；
- 能量 0-100 实时调整；
- 心情笔记与总结；
- 手动保存与 500-1000ms 防抖自动保存并存；
- 按日期查看且严格隔离；
- Dashboard 当日联动。

#### 9.4.4 验收标准

- 同一天只能存在一条主记录；
- 切换日期后不串数据；
- 自动保存不打断文本输入或改变光标；
- 手动保存后显示明确成功反馈；
- 刷新后心情、能量、关键词和文字均保持。

### 9.5 Tutoring

#### 9.5.1 目标

承接家教身份，明确分离学生长期信息、已发生课程和未来课程安排。

#### 9.5.2 功能范围

1. **学生管理**：姓名、年级、科目、学习情况、阶段目标、薄弱点 CRUD；
2. **学生概览**：只展示长期学生信息；
3. **课程记录**：课次、日期、时长、内容、表现、问题、作业 CRUD，按时间倒序；
4. **课程安排**：下次时间、目标、内容、材料、练习题 CRUD；
5. **删除联动**：删除学生时明确提示课程和安排的级联处理。

#### 9.5.3 验收标准

- 三个 Tab 内容互不混杂；
- 所有课程和安排按 `studentId` 隔离；
- 删除学生前必须提示关联数据数量；
- 刷新后详情路由和数据保持可访问。

### 9.6 Creation

#### 9.6.1 当前定位

承接个人创造项目，记录项目介绍、阶段、每日推进、时间投入、产出和下一步行动。

#### 9.6.2 功能范围

- 项目类型：产品、Code、内容、其他；
- 阶段：构思、开发、完成；
- 项目和推进事项 CRUD；
- 推进事项记录日期、内容、投入时间、产出和状态；
- 项目详情只展示关联推进；
- 删除项目时检查关联推进记录。

#### 9.6.3 产品待验证问题

Creation 是独立身份，还是 PM Workspace 中“个人项目”的一种类型？V1.0 保留现状，用户研究后决定是否合并入口。

### 9.7 Experience / 身心健康

#### 9.7.1 目标

将休息、体验和身体状态正当化、可视化，形成其他行动模块的承载地基。

#### 9.7.2 Experience 功能范围

- 今日放松计划 CRUD；
- 状态从 `pending` 流转为 `completed`，记录完成时间；
- 完成后保留划线卡片，不直接删除；
- 自动生成体验记录；
- 体验记录包含地点、类型、评分、开心瞬间、发现和照片占位；
- 本周活动次数、类型统计和体验总结。

#### 9.7.3 Health 功能范围

- 步数、睡眠、饮水和运动记录；
- 今日目标与近七日趋势；
- 健康数据只作个人记录，不提供医疗诊断。

#### 9.7.4 地基层联动要求

- Dashboard 显示能量、睡眠或恢复提醒；
- 当能量持续偏低时，优先建议休息或降低计划强度，而不是增加任务；
- 周复盘同时展示行动成果与恢复情况；
- 健康指标不使用羞辱性、惩罚性或排名式文案。

## 10. 跨模块规则

### 10.1 CRUD 一致性

- 新增和编辑统一使用现有 `openModal()` 系统；
- 删除必须提供确认；有关联数据时说明影响范围；
- 保存后立即刷新页面，并给出轻量反馈；
- ID 必须稳定，不能依赖数组下标；
- 列表空状态应提供下一步入口。

### 10.2 数据关联

- 子记录必须保存父对象 ID；
- 详情页必须按父 ID 过滤，不能展示其他对象数据；
- 删除父对象时采用“确认并级联删除”或“阻止删除并提示处理”，不得产生孤儿数据；
- 旧字段通过读取兜底兼容，逐步迁移，不直接破坏已有 LocalStorage。

### 10.3 状态语义

- 任务和计划状态使用统一英文枚举存储、中文/英文文案显示；
- 已完成数据默认保留，不因完成自动删除；
- 状态变化记录完成时间或更新时间；
- 周统计只读取真实完成记录。

### 10.4 保存与反馈

- 表单保存使用 `commit()`：写入 LocalStorage 并重绘；
- 连续输入使用防抖静默保存，避免光标被重绘打断；
- 保存成功使用 Toast 或页面内状态反馈；
- LocalStorage 写入失败时需向用户提示，而不只写 Console。

---

## 11. 数据与隐私需求

### 11.1 本地数据策略

- 默认数据保存在 `pos.data.v1`；
- 不上传服务端，不进行第三方共享；
- 支持 JSON 导出、导入和清空；
- 导入时校验 JSON 格式和 schemaVersion；
- 清空前二次确认，并说明不可恢复风险。

### 11.2 数据兼容

- `loadData()` 合并新增字段与旧数据；
- 旧字段只读兼容，写入时优先使用统一新字段；
- 每次结构升级更新 `schemaVersion`；
- V1.0 正式发布前提供一次数据迁移函数和回滚前导出提示。

### 11.3 敏感信息

学生信息、心情记录和健康数据属于敏感个人数据。V1.0 应明确：

- 数据仅存当前浏览器；
- 共用设备可能被其他使用者看到；
- 清除缓存可能导致数据丢失；
- 导出的 JSON 文件需由用户自行妥善保存。

---

## 12. 非功能需求

### 12.1 响应式与可用性

- 支持手机和桌面浏览器；
- 桌面侧栏与手机底栏入口顺序一致；
- 导航切换后路由、选中态和正文一致；
- 主要触控目标不小于 44×44px；
- 表单在手机软键盘弹出时仍可滚动和保存。

### 12.2 性能

- 首次可交互时间目标：常见网络环境下不超过 3 秒；
- 单次页面切换无明显卡顿；
- 记录达到 1000 条时，常用列表仍可在 1 秒内完成渲染；
- CDN 不可用时应提供明确提示或后续改为本地依赖。

### 12.3 稳定性

- JavaScript 语法检查通过；
- 所有主路由和子路由加载时 Console 无未捕获异常；
- 空数组、缺失字段、旧版数据均不应导致白屏；
- 写入失败、导入失败提供用户可见反馈。

### 12.4 无障碍

- 图标按钮提供 `aria-label` 或 title；
- 颜色不作为状态的唯一表达方式；
- 表单字段具备可识别 label；
- 键盘可访问主要按钮和 Modal；
- 文本与背景满足基本对比度要求。

### 12.5 国际化

- 中文和英文切换不丢失数据；
- 状态值使用语言无关枚举；
- 新增功能不可只硬编码中文，正式发布前补齐 i18n key。

## 13. 成功指标

### 13.1 北极星指标

**每周完成至少 3 个身份板块有效记录的活跃用户比例。**

“有效记录”指用户主动新增或更新的真实数据，不包括浏览和示例数据。

该指标同时衡量：系统是否承接了多重身份，以及用户是否持续使用，而非单纯追求任务数量。

### 13.2 核心指标

| 指标 | 定义 | V1 验证目标 |
|---|---|---|
| 首次价值时间 | 首次打开到完成第一条记录 | ≤ 3 分钟 |
| 周活跃记录天数 | 一周内至少创建/更新一条记录的天数 | ≥ 3 天 |
| 跨模块使用率 | 一周内使用至少 3 个身份板块 | ≥ 50% 测试用户 |
| 周复盘完成率 | 有周记录用户中完成周复盘的比例 | ≥ 30% |
| 7 日留存 | 首次记录后第 7 天仍有行为 | 用户测试阶段持续观察 |
| 数据恢复成功率 | 导出后可重新导入 | 100% 测试用例 |

### 13.3 质量指标

- 主流程阻断级错误为 0；
- CRUD 自动化/手动验收通过率 100%；
- 路由白屏率 0；
- LocalStorage 刷新后丢失率 0（用户主动清除数据除外）。

### 13.4 反指标（Guardrails）

- 用户填写一条记录的字段数量持续增加；
- 用户为维护系统花费的时间超过实际行动时间；
- 低能量时系统继续强化任务压力；
- 预设模块让用户认为“不适合我”或不知道从何开始。

## 14. 用户体验与文案规范

### 14.1 语气

- 温和、具体、不评判；
- 强调“被记录”和“持续一点点”；
- 避免“你失败了”“落后”“必须完成”等压力表达；
- 低能量状态优先提供恢复建议。

### 14.2 反馈示例

- 保存成功：`✅ 已保存，今天的你被好好记录下来了。`
- 完成任务：`完成了一步，已经很不错。`
- 完成休息：`✅ 这段休息也属于今天的重要进展。`
- 空状态：`从一条简单记录开始吧。`
- 低能量：`今天能量偏低，先把计划调轻一点也可以。`

### 14.3 视觉原则

- 保持现有卡片、pill/tag、柔和色彩、圆角和留白；
- 不用红色大面积表达未完成；
- 完成态保留可见，使用划线、灰度和正向标签；
- 身心健康使用贯穿性的柔和状态表达，而非警报式仪表盘。

## 17. 风险与应对

| 风险 | 影响 | 应对策略 |
|---|---|---|
| 预设结构过多 | 新用户不知道从哪里开始 | 首次引导只推荐 1-2 个模块；支持显隐 |
| 结构过死 | 用户产生“不属于我”感 | 固定骨架，允许卡片顺序、字段和目标局部自定义 |
| 单文件复杂度持续上升 | 维护和回归成本增加 | V1 不重构，但建立函数命名、数据 schema 和逐路由测试清单 |
| LocalStorage 丢失 | 用户长期记录不可恢复 | 强提示 + 定期导出提醒 + 导入校验 |
| 示例数据与真实数据混淆 | Dashboard 产生虚假反馈 | 首次使用明确标记示例或提供一键清空 |
| 过度量化身心状态 | 增加焦虑 | 采用描述性反馈，不排名、不惩罚 |
| AI 模拟输出被误认为真实能力 | 信任受损 | 明确标注模拟；真实 API 接入前不宣称 AI 已生成 |
| 跨模块字段不一致 | 统计与联动出错 | 使用稳定 ID、统一状态枚举和数据迁移策略 |

## 20. 最终产品判断

Personal-OS 的竞争力不在于比 Notion 更自由，也不在于比传统待办工具更高效，而在于它能否用足够低的记录成本，把一个人的多重身份、行动过程和身心状态放回同一张完整图景中。

V1.0 的关键不是继续增加模块，而是证明三件事：

1. 预设结构确实比自由搭建更快产生价值；
2. 多身份被统一看见，确实能降低割裂和愧疚；
3. 将身心健康设为地基，确实能让用户更可持续地行动。

只有这三点被真实用户验证，Personal-OS 才不仅是一个功能完整的个人管理原型，而是一款具有独立产品价值的个人操作系统。
